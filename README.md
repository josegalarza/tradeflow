**A local-first analytics engineering platform for a synthetic retail brokerage.**
dbt · DuckDB · Dagster · Dash — dimensional modelling, a tag-driven data
classification and masking framework, quarantine-based data quality, CI/CD and
Slack alerting.

**Requires:** Python 3.11 or newer, and nothing else. `make install` finds a
suitable interpreter itself; point it at one with
`make install PYTHON_BIN=/path/to/python3.12` if it cannot.

```bash
git clone https://github.com/josegalarza/tradeflow && cd tradeflow
make install
make demo
```

Two minutes later you have a warehouse of 26 hand-written models plus 40
generated role views, built from 430,000 synthetic rows, with 267 data tests and
5 unit tests passing, and a generated data catalog. No cloud account, no
credentials, no bill.

> **The data is synthetic.** Instrument symbols, names, sectors, exchanges and
> listing currencies are real-world reference data. Every price is a simulated
> random walk, and every customer, account, order and fill is generated by
> `ingestion/generate.py`. This is not market data and not investment advice.

---

## Why this exists

A brokerage is a good vehicle for a warehouse because it forces the problems that
make analytics engineering hard, rather than letting you pick the easy version of
each:

| The problem | Where it shows up here |
|---|---|
| Attributes change and history matters | `dim_customer` is Type 2 — a trade placed while a customer was `medium` risk stays attributed to `medium` risk |
| Facts arrive at different grains | One fact of each Kimball type: transaction, accumulating snapshot, periodic snapshot |
| Money exists in several currencies | ASX in AUD, European listings in EUR/GBP, everything converted once in one model |
| Positions exist on days markets don't | An `ASOF JOIN` carries the last close forward — 28% of position rows are priced this way |
| Source data is dirty | A quarantine layer that records *why* a row was rejected, and a gate on the rejection *rate* |
| Not everyone may see everything | Every column classified; four role views generated from those tags |

## Architecture

```
  ingestion/generate.py                 --scale tiny|small|medium|large
        │                                  67M rows in 172s at `large`
        ▼
  data/landing/**.parquet               Hive-partitioned. dbt reads it in place.
        │
        ▼
  ┌──────────────────────────────────────────────────────────────────────┐
  │ 10_staging        9 models · views · 1:1 with source                 │
  │                   rename, cast, dedupe. No joins, no business logic. │
  │                   Every column classified.                           │
  ├──────────────────────────────────────────────────────────────────────┤
  │ 20_intermediate   6 models · business logic, FX, the quarantine      │
  │                   boundary. Never exposed to BI.                     │
  ├──────────────────────────────────────────────────────────────────────┤
  │ 30_marts         11 models · tables · 4 dimensions, 4 facts,         │
  │                   3 aggregates. The contract with BI.                │
  ├──────────────────────────────────────────────────────────────────────┤
  │ 40_secure        40 models · GENERATED · one masked view per role    │
  │                   per mart, from the classification tags.            │
  └──────────────────────────────────────────────────────────────────────┘
        │
        ├── Dash app (5 pages)      ── Dagster (78 assets, 244 checks)
        └── static HTML export      ── dbt docs + generated data catalog
```

The layer rule — **a model may reference only its own layer and the one below** —
is enforced by `governance/check_layer_boundaries.py` in CI, not by convention.
Conventions decay. There is exactly one exemption (`dim_date`, which needs the
observed date range) and it carries a written reason that the check prints on
every run.

## The parts worth reading

### 1. A classification framework that cannot rot

Every column carries governance metadata in the dbt schema files:

```yaml
- name: email
  description: Primary contact email, lowercased and trimmed.
  meta:
    classification: restricted        # public | internal | confidential | restricted
    pii: true
    pii_type: email
    masking: hash                     # hashed, not redacted: analysts still need
                                      # distinct counts and cross-system joins
```

Three tools read those tags out of `manifest.json`. None of them contains a
hardcoded column name:

- **`check_classification.py`** — the CI gate. An untagged column in staging, or
  any column of a PII-bearing model, fails the build. It reads `catalog.json` for
  the columns that *physically exist*, not just the ones somebody documented — so
  an undocumented `national_id` cannot slip through the gate designed to catch it.
- **`generate_secure_views.py`** — emits 40 views, one per role per mart. Committed
  to the repo so the SQL each role sees is reviewable in a pull request, and
  verified with `--check` in CI so a new mart column cannot stay unmasked.
- **`build_catalog.py`** — renders [`docs/catalog.md`](docs/catalog.md), including a
  PII register: every personal-data column, its masking strategy, and how each role
  sees it. That is the artefact a subject-access request actually needs.

Run `make roles` to see one customer through every lens:

| Column | `marts` (data team) | `auditor` | `support` | `analyst` | `marketing` |
|---|---|---|---|---|---|
| `full_name` | Eleanor Pearce | Eleanor Pearce | Eleanor Pearce | *redacted* | *withheld* |
| `email` | eleanor.pearce+…@example.net | *same* | `e***@example.net` | `e653598681d5…` | *withheld* |
| `phone_number` | +15 438 668 411 | *same* | `*** *** 411` | `*** *** 411` | *withheld* |
| `national_id` | 953-65-3319 | *same* | *redacted* | *redacted* | *withheld* |
| `date_of_birth` | 1988-03-12 | *same* | `1980s` | `1980s` | *withheld* |
| `postcode` | 1993 | *same* | 1993 | `19**` | *withheld* |
| `risk_rating` | medium | medium | medium | medium | *withheld* |

Four decisions in there are worth defending:

- **It fails closed.** A sensitive column with no declared masking strategy is
  redacted, not passed through. A governance framework that fails open is worse
  than none, because it is trusted.
- **`marketing` withholds rather than masks.** A masked column still advertises
  that the data exists and invites a request for access to the real thing.
- **Exceptions are allowed but must be justified.** `ip_address_prefix` is a
  deliberately truncated /24, classified `internal` so analysts have a safe
  alternative to the raw address. It passes the gate only because it declares a
  written `classification_rationale`, which appears in the catalog. Undocumented
  exceptions fail.
- **`tokenize` is declared and deliberately unimplemented.** Requesting it raises
  an error rather than silently substituting a hash, because a fake token vault
  misrepresents the control.

**What this is not:** DuckDB has no engine-level masking or row-level security.
This enforces policy at the *modelling* layer — real, if access is mediated by
schema grants, and bypassed completely by anyone with direct access to `marts`.
The same tags would drive Snowflake masking policies or BigQuery policy tags,
where the engine enforces. Being exact about that boundary matters more than the
demo looking impressive. → [ADR 0003](docs/adr/0003-tag-driven-masking-not-engine-enforced.md)

### 2. Data quality that degrades instead of stopping

```bash
make demo-anomalies    # plants duplicate fills, orphan FKs, negative
                       # quantities, over-fills, back-dated fills, null PII
```

The result is the interesting part:

```
4 detector WARNINGS   ·   1 gate ERROR   ·   all 11 marts built
```

The quarantine absorbed the defective rows across six reason codes, and
`marts.agg_data_quality` records what and why. The only models that do not build
are the four role views over `agg_data_quality` itself — they sit downstream of
the gate that failed, which is dbt doing exactly the right thing.

That split is deliberate. A staging test at error severity halts every downstream
model — so when the defect is one the quarantine is built to absorb, the dashboard
goes dark because 0.15% of orders were malformed. Worse than the defect. So:

- **Detectors warn.** Orphan foreign keys, duplicate fills, negative quantities.
  Reported loudly, quarantined with a reason, counted in the marts.
- **The gate errors.** `assert_reject_rate_within_threshold` fails when any single
  day's rejection *rate* exceeds 0.1%. One bad row is operational noise; a rate is
  an incident.
- **Invariants error.** The accounting identity, mart grain uniqueness, FX
  resolution — things that cannot be legitimately violated.

CI asserts both halves: [a dedicated job](.github/workflows/ci.yml) builds
deliberately corrupted data, requires the build to fail, and then requires the
marts to have been built anyway. A test suite that has never caught anything is
indistinguishable from one that cannot.

**The strongest test in the repo** is
[`assert_account_cash_reconciles_to_source.sql`](warehouse/tests/assert_account_cash_reconciles_to_source.sql).
`fct_account_daily.cash_balance_reporting` is built with window functions over a
date spine carrying an opening balance — exactly the SQL that produces plausible,
smooth, wrong numbers. So the test ignores the model's arithmetic entirely and
rebuilds the balance from the atomic sources. Two routes to one number.

It found a real bug: twelve accounts had fills dated *before the account existed*.
An order placed on the final Saturday of the window had no next trading session to
roll into, so it rolled backwards. That is now
[`assert_no_activity_before_account_opened.sql`](warehouse/tests/assert_no_activity_before_account_opened.sql).

### 3. One fact of each Kimball grain

| Model | Grain | Type | Why it is that type |
|---|---|---|---|
| `fct_executions` | one fill | **transaction** | Fully additive. Can answer questions nobody has asked yet. |
| `fct_orders` | one order | **accumulating snapshot** | An order is a *process*: placed → first fill → resolved. The measures that matter are the lags between milestones. |
| `fct_positions_daily` | account × instrument × day | **periodic snapshot** | Semi-additive. Incremental, with only non-zero holdings materialised. |
| `fct_account_daily` | account × day | **periodic snapshot** | Cash, equity, and a realised/unrealised P&L split. |

`fct_positions_daily` is where the modelling gets real. The naive spine —
accounts × instruments × days — is 1.1 *billion* rows at `medium` scale, almost all
zero. Instead the running balance is computed where it changes, turned into the
interval it stayed valid for, and only those intervals expand to daily rows:
**1.4M rows instead of 59M** at `small`. → [ADR 0005](docs/adr/0005-position-snapshot-window.md)

And `dim_customer` is Type 2 built from periodic extracts rather than
`dbt snapshot`, because snapshots can only accumulate history over real elapsed
time — meaning the SCD2 story would be invisible on a fresh clone and untestable in
CI. Five dbt unit tests cover the boundary logic against fixed fixtures rather
than against whatever the data happens to contain.
→ [ADR 0004](docs/adr/0004-scd2-from-extracts-not-snapshots.md)

### 4. A generator that makes the rest demonstrable

`ingestion/generate.py` is 1,600 lines and does three things no public dataset
could:

- **Scales across four orders of magnitude.** `--scale large` produces **67.4M rows
  in 172 seconds** (11M orders, 39M events, 3 GB of Parquet, 4.5 GB peak RAM) —
  which is what makes the incremental models and partition pruning *necessary*
  rather than decorative.
- **Carries a controllable PII surface.** Names, emails, phones, dates of birth,
  national IDs shaped like the real formats per country, street addresses, and IP
  addresses. The classification framework has something real to classify.
- **Plants defects on request.** `--inject-anomalies`, mapped to named tests.

It is also internally coherent in ways that took work. Funding is derived from
trading appetite: the first version had customers trading far more than they ever
deposited, so platform cash was **−$88M** against +$266M of holdings and 27% of
account-days were overdrawn. Every balance-sheet number in the warehouse was
meaningless. Deposits are now a function of `orders/day × notional × (2p−1) ×
active_days`, and the lognormal mean factor that a first pass gets wrong.

## Stack, and what each choice cost

| Concern | Choice | The trade |
|---|---|---|
| Warehouse | **DuckDB** | Real columnar OLAP with `ASOF JOIN` and `QUALIFY`, zero setup, runs in CI. No engine-enforced security — hence ADR 0003. |
| Transform | **dbt-core** | Tests, docs, unit tests, and a `manifest.json` that the whole governance layer is built on. Model config is split across `.sql` and `.yml`, and the drift that invites is now caught by a check. |
| Orchestration | **Dagster** | 78 assets, 244 asset checks, the model graph *is* the asset graph. Costs a dbt minor version: `dagster-dbt` requires `dbt-core<1.12`. |
| BI | **Dash** + static export | Interactive locally, published as self-contained HTML so a reviewer sees charts without cloning. |
| CI/CD | **GitHub Actions** | Free for public repos, and the artefacts *are* the portfolio. |

Full reasoning, including what each rejected alternative would have been better
at, is in [`docs/adr/`](docs/adr/).

## Known limitations

Stated because a portfolio project that claims no limitations is not being
straight with you:

- **Position cost basis is net capital deployed, not weighted-average cost.** True
  average-cost accounting is inherently sequential; the column is named
  `net_invested_reporting` for what it is rather than what it might be mistaken
  for. → ADR 0005
- **Daily partitions with backfill are not implemented.** The generator rewrites
  its whole window, so partitions would be a UI affordance over an asset that
  cannot materialise one day. Faking it would look better and behave worse.
  → ADR 0006
- **`fct_positions_daily` covers a trailing 120 days**, not full history, and
  `fct_account_daily` shares that window.
- **The position reconciliation test samples** 5,000 rows rather than checking
  exhaustively; its correlated subquery is O(snapshots × fills).
- **Simulated prices have generous drift.** Portfolio returns look better than any
  real broker's book. It is a random walk with a positive drift parameter, not a
  forecast.
- **Charts commit to a single light surface.** A half-implemented dark mode that
  leaves the plot area light is worse than an honest one.
- **The container path is written but not yet verified end to end.** The
  `Dockerfile`, entrypoint and compose file are complete, and `.dockerignore`
  brings the build context down from 1.1 GB to 0.9 MB — but the machine this was
  built on could not complete a `docker pull` of the base image (the daemon
  stalls; the registry itself answers fine over HTTPS), so `make up` has never
  been observed to come up. Everything else in this README was run and checked.
  Treat the Docker path as untested until it has a green run behind it.
